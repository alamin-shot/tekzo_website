## Boundary assertions (Q5: at most one checked guard per boundary)

| Boundary | Helper | Reason |
|---|---|---|
| zod issue path → `keyof ServerEnv` | `isServerEnvKey()` type guard in `src/config/env.server.ts` | `issue.path[0]` is a `PropertyKey`. Narrowed with a guard, no `as` |
| Backend / request JSON (`response.json()`, `request.json()`) | Always assigned to an `unknown` variable, then read through `src/lib/json.ts`: `isRecord`/`rec` (`a?.b`), `isList` (`Array.isArray` narrowing to `unknown[]`, not `any[]`), `fieldsOf` (destructuring), `orList` (`x \|\| []`), `requireString`, `errMessage`, `isNextRedirect`, `toDateInput` | One shared set of guards for every JSON boundary. Type predicates only, no `as` |
| Caught errors (`catch (err)`) | `errMessage(err)`, `rec(err)?.status`, `rec(err)?.name` | `err` is `unknown` under `strict` |
| CMS values in typed JSX (P4) | `src/lib/render.ts`: `str()` for string props, `nodeOf()` for children; plus `lowerOpt`, `firstOf`, `mapOpt`, `lengthOf` in `src/lib/json.ts` (`x?.toLowerCase()`, `x[0]`, `x?.map()`, `x.length`) | Same JS semantics, including where the JS threw |

## P3 store decisions (locked in, 26 Nov 2026)

The three stores stay as built. As decided, no placeholder stores are created for POS, auth session or guest cart.

| Decision | Reason |
|---|---|
| Three stores that **replace existing state**: `counter.store` (cart/wishlist badges), `compare.store` (compare slots), `dashboardUi.store` (dashboard theme, sidebar, points) | These are the three pieces of shared client state that exist today (SYSTEM_MAP §6). The contexts become thin compatibility wrappers, so no component changed |
| **No separate store yet for POS / `purchase_point`** | There is no POS or loyalty client state to move: `purchase_point` is only read from API product data and copied into cart/buy-now payloads. A store would hold nothing. The value is typed in `types/pos.ts` and will be used when ProductDetails/checkout are converted (P6/P8) |
| **No auth-session store yet** | Session state today is the `has_auth` cookie (read at call time by `hasAuthCookie()`), plus `NavAuthClient`'s own `cachedNavUser` cache and the `userProfileUpdated` event. Moving those into a store would mean rewriting `NavAuthClient` (P4) and its timing; done there, with its own parity check |
| **No guest-cart store yet** | `localStorage.cart` has about 15 writers with drifting shapes (bug #1). A store now would either be unused or require rewriting those components; done with checkout in P8 behind a `guestCartStorage` wrapper, as planned |
| No Zustand `persist` middleware | It stores `{"state":…,"version":0}` under one key, which would change the `compareProducts` JSON (read directly by the compare page) and merge the three `dash_*` keys. Hydration is a manual `hydrate()` action called from the provider's mount effect, with the same keys and values as before |
| Stores are module singletons; nothing writes to them on the server | All actions run from client effects or handlers, so server renders always see the defaults (`0/0`, `[null,null]`, light / expanded / points shown): the same first render as the old `useState` defaults, so no hydration mismatch |
| The hooks still throw outside their provider | A one-boolean marker context per provider keeps the old "must be used inside …Provider" errors, although the store itself would work anywhere |

## Setup decisions (P1)

| Decision | Reason |
|---|---|
| TypeScript **6.0.x** (`~6.0.3`), not 7 | `eslint-config-next` lints `.ts` files through `@typescript-eslint/parser` 8.73, which needs the TypeScript JS API (removed in TS 7) and supports `typescript <6.1.0` |
